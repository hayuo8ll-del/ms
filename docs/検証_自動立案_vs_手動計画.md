# 検証: 自動立案の計画は、手で立てている計画になっているか

対象: `claude/production-planning-automation-6l0150` (`58b0fd0`)
検証日: 2026-07-29

## 結論(先に)

**まだ「同じ計画」にはなっていない。** ただし外れ方には筋が通っていて、原因も特定できる。

- **月次の総量・シフトモード選択のレベルでは合っている。** 需要をボトルネック(HAL)日次能力で
  割り付けるという骨格は現場の考え方どおりで、テスト100件も全て通る。
- **製番ごとの日付レベルでは合っていない。** リポジトリ自身が記録している実照合結果で、
  完成日の平均絶対誤差 **2.66稼働日**(較正前3.12)、投入日 **2.4稼働日**。
  22稼働日の月計画で1ロットあたり平均2〜3日ずれるのは、そのまま現場表として使える精度ではない。
- **さらに、その 2.66 という数字自体が実力より甘く出る作りになっている。** 照合ロジックに
  4つの計測バイアスがあり(下記 B-1〜B-4)、実際の乖離はこれより大きい可能性が高い。
- **日付がずれる最大の構造要因は「A勤限定切替」の実装方法**(下記 A-1)。設計意図として
  書かれている「別号機グループでの同日並行生産」を、この制約が塞いでしまっている。

まず A-1 と B-1 を直してから、再度 FeliCa 照合の数字を取り直すことを勧める。

---

## 検証方法

現物の Excel(THM生産台帳・FeliCa実計画・THM短期投入予定表・TA1_投入計画)はリポジトリに
含まれていないため、**実データそのものの再照合はできていない**。代わりに次を行った。

1. `cd backend && python3 -m pytest` — **100 passed**(既存テストは全て通る)
2. 照合機構(`felica_calibration.py`)を、正解が既知の合成データで検証
3. 実 config (`config/bottleneck_planning.json`) を使い、1か月分のフル需要で立案して挙動を計測

再現スクリプトの要点は本文中に埋め込んである。

## A. 計画そのものが手計画とずれる要因

### A-1. 【最重要】A勤限定切替が、同日並行生産を潰している

`allocate_bottleneck` の docstring はこう書いている:

> キャパの小さい機種(例: Lite-S)が残したライン能力は、同日に別機種が別号機グループで
> 並行して使う(現場のTA1_生産計画と同じ形)

ところが同じ関数の A勤限定切替は、その並行投入を「切替」とみなして塞ぐ。判定に使っている
`used_fraction = 1 - line_remaining / cap_today` は **ライン全体の消化率**であって、
時刻の代理にはなっていない。別号機グループが朝から空いていても、先行機種がライン能力を
食っていれば「もうB勤だから切替不可」と判定されてしまう。

実 config・1か月フル需要(さそり金融600k / SuicaⅢ500k / Lite-S 300k / MOT2 200k)での実測:

| | A勤限定切替 ON(現行) | OFF |
|---|---|---|
| HAL投入計 | 1,530,000 | **1,600,000**(需要どおり) |
| 複数機種が同日並行した日数 | **9 / 23日** | 21 / 23日 |
| 納期遅れ製番 | S2, S3 | S3 のみ |
| A勤繰下げ警告 | 37件 | 0件 |

7月上旬の HAL はこうなる:

```
ON : 07-01 {さそり金融 80,000}                  計 80,000/90,000  ← 10,000 遊ぶ
OFF: 07-01 {さそり金融 80,000, SuicaⅢ 10,000}   計 90,000/90,000
```

さそり金融の機種キャパ80k/日はライン能力90k/日を使い切れないので、毎日10,000台分の能力が
遊ぶ。現場の TA1_生産計画なら別号機グループで別機種を流している枠である。結果として
**月70,000台の取りこぼしと、製番S2の納期遅れ1件が、モデルの副作用として発生している。**

> 直し方の方向: 切替可否の判定を「ライン消化率」ではなく **その機種が使う号機グループの
> 消化率**(または明示的な時刻/勤務帯)で行う。少なくとも、先行機種のキャパ上限で余った
> 能力を別機種が埋めるケースは切替扱いから外す。

### A-2. A勤繰下げ警告が事実と違い、かつ大量に出る

警告文は「翌稼働日の朝に開始します」と言うが、翌日も同じ理由で再び繰り下がるため、
実際には開始しない。上記条件では同一機種の同一文言が **37件**並び、その中に埋もれて
本当に見るべき警告(納期超過2件、能力不足2件)が読めなくなっている。

```
SuicaⅢ: ...2026-07-01中の切替を避け翌稼働日の朝に開始します。
SuicaⅢ: ...2026-07-02中の切替を避け翌稼働日の朝に開始します。   ← 翌朝も開始していない
SuicaⅢ: ...2026-07-03中の切替を避け翌稼働日の朝に開始します。
（以下 07-10 まで継続）
```

機種ごとに集約し、文言を「〜まで開始できません」に改めるべき。

### A-3. 上流/下流工程の台数が、計画期間の端で静かに消える

`expand_to_stages` は稼働日オフセットで工程を前後にずらすが、**期間外に出たセルは
破棄され、工程あたり1行の汎用警告になるだけ**で、どの機種の何台が消えたかは出ない。

実 config(ANT -1 / TAL -2 / MIL +2)・需要160万台での実測:

| 工程 | 計画に載った台数 | 需要比 | 欠損 |
|---|---|---|---|
| ANT | 1,450,000 | 90.6% | 150,000 |
| TAL | 1,370,000 | **85.6%** | 230,000 |
| HAL | 1,530,000 | 95.6% | 70,000(能力不足・警告あり) |
| MIL | 1,430,000 | 89.4% | 170,000 |

画面と Excel の「生産計画(機種×日)」の TAL 行は、**需要の85%しか表示していない**。
この表を見て材料を手配すると2日分足りない。手計画にはそんな穴はないので、ここは確実に
食い違う。月初の上流投入は前月計画からの繰り越し(前段WIP)として明示的に扱うか、
計画期間を実際より前後に広げて立案し、表示だけ当月に絞るのが筋。

### A-4. 祝日がデフォルトで稼働日として数えられている

`config/bottleneck_planning.json` の `nonWorkingDays` は **空**。FeliCa の灰色セルを
`/api/bottleneck/apply-calendar` で取り込むまで、祝日は稼働日のままになる。

```
7月の稼働日数(現行config) = 23
海の日 2026-07-20 は稼働日扱い? True (月曜)
祝日を入れた場合 = 22 稼働日 → 16Hで 90,000台の能力過大計上
```

祝日1日で90,000台(1日分)を余計に積むので、月末に向かって計画全体が1日ずつ前にずれる。
**照合の前に必ずカレンダー取込を実行する**運用にするか、祝日を config の初期値として
持たせる必要がある。

## B. 「合っているか」を測る照合機構自体のバイアス

照合の骨格は健全である。**自分の計画をそのまま FeliCa 形式にして読ませると、完成日MAE・
投入日MAE・日次形状MAE がすべて 0 になる**ことを確認した(往復テスト)。以下は、その上で
実データに効いてくる系統的な甘さ。

### B-1. 較正が「現行config」を再現できていない — `_with_offsets` が機種別オフセットを落とす

`felica_calibration._with_offsets` は `StageFlowConfig` を4引数で作り直しており、5番目の
`lead_offset_by_product`(機種別オフセット上書き)が欠落する。

```
入力 MIL.lead_offset_by_product = {'さそり金融': 5}
_with_offsets 通過後            = None
offset_for('さそり金融'): 前 = 5 / 後 = 2
```

結果、`calibrate()` が「現行値」として提示する誤差は、config に機種別オフセットが入って
いる場合、**実際に立案される計画とは別物の計画**に対する誤差になる。

```
機種別オフセット(+5)を効かせた計画の MIL完成日 = 2026-07-09
calibrate内部(_with_offsets後)の MIL完成日     = 2026-07-06   ← 3日ずれ
```

現在の config は機種別オフセットを採用していないので**今は影響が出ていない**が、
Phase 4 の機能を使った瞬間に較正結果が壊れる。1行の修正で済むので先に直すべき。

### B-2. 計画期間外の日付が端の稼働日へ丸められ、「照合できた」ことになる

`_nearest_index` は稼働日でない日を最寄りの稼働日に丸めるが、**期間外の日付も丸める**。

```
FeliCa側の日付 2026-04-01 → 稼働日index 0  (2026-07-01)
FeliCa側の日付 2026-12-25 → 稼働日index 22 (2026-07-31)
```

4月完成の FeliCa ロットを7月計画と照合すると `matched=1, completion_mae=6.0` になる。
実際は約3か月ずれているのに、誤差は計画期間の幅(22)で頭打ちになる。前月からの繰り越し
ロットや期間をまたぐロットが混ざると、**MAE が実力より小さく出る**。期間外は
`None` を返して母数から外すのが正しい。

### B-3. 同日carryover除外が、通常ロットの日次を削りすぎる

「同一日に Line-In と Completion の両方に台数がある日 = 先週までの計画台数」という前提で
その日を両系列から落としているが、リードタイム数日のロットが連続流動している期間は、
投入と完成が同日に並ぶのが**正常**である。

リードタイム2稼働日の普通のロット(8日間流動)で試すと:

```
元データ: Line-In 8日 / Completion 8日
除外後  : Line-In 2日 / Completion 2日   ← 中間6日が消える
```

初日と最終日は残るので `line_in_first` / `completion_last`(=完成日MAEの母数)は守られるが、
**日次形状MAE の母数が壊れる**。CLAUDE.md が「日次形状の差は lump-vs-rate の構造差なので参考値」
と結論づけている根拠の一部は、この除外による人工的な差である可能性がある。
また、投入から完成まで1日で終わる小ロットは**丸ごと消えて照合対象から外れる**
(既存テストの `C1` ケースがまさにそれ)。**短納期ロットが精度評価に含まれていない。**

判定条件を「Line-In合計 ≒ Completion合計 かつ その日で完結」のように狭めるべき。

### B-4. 較正の推奨値が探索グリッドの端に貼りついている

`calibrate` の探索範囲と、その結果 config に採用された値:

| パラメータ | 探索範囲 | 採用値 | 位置 |
|---|---|---|---|
| ANT | (-3, -2, **-1**) | -1 | **上端** |
| TAL | (**-2**, -1) | -2 | **下端** |
| MIL | (0, 1, **2**) | 2 | **上端** |
| A勤割合 | (**0.4**, 0.5, 0.6) | 0.4 | **下端** |

**4つ全部が範囲の端**。これは最適値がグリッドの外にあることを強く示唆する。
つまり MAE 2.66 は「探索範囲内での最良」であって、収束した値ではない。
範囲を広げて(例 ANT 0..-5 / TAL 0..-5 / MIL 0..5 / A勤 0.2..0.8)再較正すれば
まだ下がる余地がある。ただし32製番に対して54通りを試す形なので、範囲拡大と同時に
**過学習の確認(期間を分けた検証)**もセットで必要。

なお `calibrate` は設備停止を無効化して較正する一方、実運用の計画は設備停止を反映して
立案するため、較正で得たオフセットは停止のない世界に最適化されている点にも注意。

### B-5. 細かい点

- **`matched` は完成日のペア数のみ。** 投入日MAEの母数は画面に出ない。完成日が無く
  投入日だけ一致するロットは `matched=0` と表示されるのに `start_mae` は計算されている。
- **役割ラベルの表記ゆれで照合が黙って0件になる。** 製番(col4)は `.strip()` しているが、
  `role == "Line-In"` は完全一致比較。末尾に空白があるだけで読み取り0件になり、
  「照合できた製番 0」とだけ表示されて原因が分からない。実測で確認済み。
- **`parse_felica_plan` は Completion が必ず Line-In の次行にある前提**(`r += 2`)。
  行が入れ替わったり空行が挟まると崩れる。

## C. まとめ: 何を直せば「手計画と同じ」に近づくか

優先順位順。

| # | 項目 | 効果 | 難易度 |
|---|---|---|---|
| 1 | A勤限定切替の判定を号機グループ単位(または時刻)に変える (A-1) | 同日並行が復活し、日次形状が現場表に近づく。月70,000台の取りこぼしと納期遅れ1件が解消 | 中 |
| 2 | `_with_offsets` に `lead_offset_by_product` を渡す (B-1) | 較正の「現行値」が正しくなる | 小 |
| 3 | `_nearest_index` で期間外を `None` にする (B-2) | MAE が実力を表すようになる | 小 |
| 4 | 上流/下流の期間外セルを WIP として明示 or 期間を広げて立案 (A-3) | TAL行の15%欠損が解消 | 中 |

| 6 | carryover 除外条件を狭める (B-3) | 日次形状の評価が意味を持つ。小ロットが評価対象に入る | 小 |
| 7 | 較正グリッドを広げ、期間分割で過学習を確認 (B-4) | MAE 2.66 からさらに改善余地 | 小 |
| 8 | A勤繰下げ警告の集約と文言修正 (A-2) | 本当に見るべき警告が読めるようになる | 小 |
