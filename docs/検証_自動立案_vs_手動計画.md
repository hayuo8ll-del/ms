# 検証: 自動立案の計画は、手で立てている計画になっているか

対象: `claude/production-planning-automation-6l0150` (`58b0fd0`)
検証日: 2026-07-29
使用した実データ: THM生産台帳2026 / THM短期投入予定表 / TA1_投入計画(7-8月) / FeliCa実計画

## 結論(先に)

**まだ「同じ計画」にはなっていない。** 取り込み(パース)は全ファイル正常だが、
**割り付けロジックが現場の流し方を再現していない。**

最も分かりやすい証拠 — 7/29〜7/31 の HAL 投入:

| 日 | あなたのTA1計画 | 自動立案 |
|---|---|---|
| 7/29 | **90,000** = Lite-S 40k + MOT2 20k + SuicaⅢ 20k + さそり交通 10k | **60,000** = MOT2 のみ |
| 7/30 | **90,000** = Lite-S 20k + SuicaⅢ 40k + さそり交通 10k + さそり金融 20k | **57,000** = MOT2 のみ |
| 7/31 | **90,000** = 同様に4機種 | **53,000** = MOT2 のみ |

あなたは毎日4機種を並行させてライン能力を使い切っている。自動立案は1機種しか流さず、
ライン能力の半分近くを空けている。**A勤限定切替の実装方法**が原因(下記 A-1)。

7月の実績(TA1赤字)で見ると、あなたのラインは **13稼働日すべてで複数機種を並行**させ、
**平均3.38機種/日**。自動立案は平均2.29機種/日で、しかも立ち上がりの3日は1機種。

FeliCa実計画との製番単位の照合では **完成日MAE 8〜9.4稼働日**(CLAUDE.md記載の2.66ではない)。

## A. 計画そのものが手計画とずれる要因

### A-1. 【最重要】A勤限定切替が、同日並行生産を潰している

`allocate_bottleneck` の docstring はこう書いている:

> キャパの小さい機種(例: Lite-S)が残したライン能力は、同日に別機種が別号機グループで
> 並行して使う(現場のTA1_生産計画と同じ形)

ところが A勤限定切替は、その並行投入を「切替」とみなして塞ぐ。判定に使っている
`used_fraction = 1 - line_remaining / cap_today` は **ライン全体の消化率**であって、
時刻の代理になっていない。別号機グループが朝から空いていても、先行機種がライン能力を
食っていれば「もうB勤だから切替不可」と判定される。

7/29時点の残需要(2,403,582台 / 60製番)を 7/29〜8/31 に立案した実測:

| | A勤限定切替 ON(現行) | OFF |
|---|---|---|
| **納期遅れ製番** | **16** | **10** |
| 遊休能力 | 484,920台 | 368,680台 |
| 平均並行機種数 | 2.29 | 2.78 |
| 立ち上がり3日 | MOT2 単独 60k/57k/53k | MOT2+SuicaⅢ+さそり交通+SD3 等 3〜5機種 |
| A勤繰下げ警告 | 40件 | 0件 |

**この制約を外すだけで納期遅れが16製番→10製番に減り、遊休能力が116,240台減る。**
そして外した後の形のほうが、あなたの実績(毎日3〜5機種並行)に近い。

あなたの7月実績の実際の姿:

```
2026-07-01 さそり金融20k + さそり交通20k + SuicaⅢ40k          = 80k
2026-07-03 さそり金融10k + さそり交通20k + SuicaⅢ30k + MOT220k = 80k
2026-07-08 さそり交通10k + SuicaⅢ10k + Lite-S30k + 部分リライト10k + MOT220k = 80k
```

なお**切替の頻度そのものは合っている**(あなたの実績 0.69回/稼働日 vs 自動立案
0.58回/稼働日)。問題は回数ではなく、「並行して立ち上げてよい」という現場の運用を
モデルが表現できていないこと。

> 直し方: 切替可否の判定を「ライン消化率」ではなく **その機種が使う号機グループの
> 消化率**(または明示的な勤務帯)で行う。少なくとも、先行機種の機種別キャパ上限で
> 余った能力を別機種が埋めるケースは切替扱いから外す。

### A-2. 祝日が稼働日として数えられている(実データで確認)

FeliCa の灰色セルには **7/20(海の日)・8/11(山の日)・8/14(お盆)** が入っている。
一方 `config/bottleneck_planning.json` の `nonWorkingDays` は **空**。

結果、あなたのTA1が 0台 と置いている日に、自動立案はフル生産を割り付ける:

```
2026-08-11  あなた 0 台  /  自動立案 120,480 台
2026-08-14  あなた 0 台  /  自動立案 115,280 台
```

祝日を反映すると工程別の欠損も一気に悪化する(下表)ので、**照合や立案の前に必ず
「非稼働日カレンダー取込(FeliCa)」を実行する**運用にするか、祝日を config の初期値
として持たせる必要がある。

### A-3. シフトモードの答えが、入力した end_date で変わる

`choose_shift_mode` は「期間需要 ÷ 稼働日数」で必要日次レートを出すため、**各ロットの
納期を見ずに**、画面で指定した終了日だけでモードが決まる。同じ台帳・同じ開始日で:

| end_date | 稼働日 | 必要レート | 選択モード | 納期遅れ |
|---|---|---|---|---|
| 2026-08-15 | 13 | 184,891 | 22h (120k/日) | 16 |
| 2026-08-31 | 24 | 100,149 | **22h (120k/日)** | 16 |
| 2026-09-15 | 35 | 68,674 | **16h (90k/日)** | 13 |
| 2026-09-30 | 46 | 52,252 | 16h (90k/日) | 13 |

9月納期のロットまで8月中に作ろうとするので 22H(夜勤増強)になる。**あなたの実績は
80〜90k/日 = 16H相当**で、22Hでは回していない。終了日の入れ方ひとつで「夜勤を増やすか」
という原価に直結する答えが変わってしまうのは危うい。必要レートは**納期までの残稼働日で
ロット別に**見るべき。

### A-4. 上流/下流工程の台数が、計画期間の端で静かに消える

`expand_to_stages` は期間外に出たセルを破棄し、工程あたり1行の汎用警告を出すだけ。
実データ(残需要2,403,582台)での実測:

| 工程 | 祝日なし(現行config) | 祝日反映後 |
|---|---|---|
| ANT | 97.5% (欠損 60,320) | 92.9% (欠損 169,920) |
| TAL | **95.1%** (欠損 117,320) | **90.6%** (欠損 226,920) |
| HAL | 100.0% | 95.4% |
| MIL | 95.4% (欠損 109,920) | **87.4%** (欠損 303,120) |

画面と Excel の「生産計画(機種×日)」の TAL 行は需要の 90〜95% しか表示していない。
この表で材料を手配すると足りなくなる。月初の上流投入は前月からの繰り越し(前段WIP)
として明示するか、計画期間を実際より前後に広げて立案し表示だけ絞るのが筋。

### A-5. A勤繰下げ警告が事実と違い、大量に出る

警告文は「翌稼働日の朝に開始します」と言うが、翌日も同じ理由で再び繰り下がるので実際には
開始しない。実データで **40件**。同一機種の同一文言が並び、その中に本当に見るべき警告
(納期遅れ16製番など)が埋もれる。機種ごとに集約し「〜まで開始できません」に改めるべき。

## B. 「合っているか」を測る照合機構のバイアス

### B-1. 【最重要】報告される精度が、計画期間の取り方で3.87〜18.18稼働日まで振れる

同じ台帳・同じ FeliCa で、期間だけを変えた実測:

| 計画期間 | future_only | 照合製番 | 完成日MAE | 完成日bias | 投入日MAE |
|---|---|---|---|---|---|
| 7/01–7/31 | true | 15 | **3.87** | −3.33 | 5.33 |
| 7/01–7/31 | false | 10 | 6.40 | −3.80 | 6.14 |
| 7/01–8/15 | true | 25 | 6.84 | +0.36 | 7.44 |
| 7/01–8/15 | false | 21 | 6.48 | +0.19 | 7.13 |
| 7/01–8/31 | true | 33 | 7.97 | +3.06 | 8.00 |
| **7/01–8/31** | **false** | **31** | **9.42** | **+5.16** | **9.19** |
| 7/01–9/30 | false | 33 | **18.18** | +15.27 | 16.81 |

**バイアスの符号すら反転する**(1か月なら「3〜4日早い」、2か月なら「5日遅い」)。
CLAUDE.md にある「完成日MAE 2.66稼働日」は、狭い窓・少ない母数(10〜15製番)での値で、
FeliCa がカバーする7〜8月全体で測ると **8〜9.4稼働日**になる。
**現状、この数字は「精度」として引用できる状態にない。**

原因は A-3 と同じで、期間を伸ばすほどシフトモードが下がって全体が後ろへ広がるため。
精度を報告するなら、**FeliCa の実データ範囲に期間を固定する**運用を決めるべき。

### B-2. 較正の推奨値がグリッドの端に貼りつき、実行ごとに変わる

`calibrate` の探索範囲と、実データでの推奨値:

| パラメータ | 探索範囲 | configの現行値 | 今回の推奨 | 位置 |
|---|---|---|---|---|
| ANT | (−3, −2, −1) | −1 | **−3** | **下端** |
| TAL | (−2, −1) | −2 | −2 | 下端 |
| MIL | (0, 1, 2) | +2 | **0** | **下端** |
| A勤割合 | (0.4, 0.5, 0.6) | 0.4 | **0.6** | **上端** |

現行 config の値(前回較正の採用値)は ANT −1 / MIL +2 / A勤 0.4 で、今回の推奨は
**すべて逆の端**。しかも4つとも範囲の端に貼りついている。これは最適値がグリッド外に
あることを示していて、較正が収束していない。改善幅も 9.42 → 8.64 稼働日と小さく、
**オフセット調整では埋まらない誤差**であることを裏づけている。

### B-3. 誤差の大半は Lite-S(Mies) 1機種に集中している

機種別の予実タイミング差(our − FeliCa、正 = 自動立案が遅い):

| 機種 | 完成日bias | 完成日MAE | 投入日bias | n |
|---|---|---|---|---|
| **Lite-S(Mies)** | **+15.0** | **16.5** | +14.0 | 12 |
| さそり金融 | +2.75 | 2.75 | +0.75 | 4 |
| SuicaⅢ | −2.36 | 4.00 | −3.73 | 11 |
| さそり交通 | −1.25 | 9.75 | −1.75 | 4 |

**Lite-S だけが3週間遅れる。** 他機種は±2〜3日程度。Lite-S は機種別キャパが
30,720/日(16H)と最も小さいため、EDD順で後回しにされると挽回できない。これは
リード時間オフセットの問題ではなく **HALのキャンペーン順序の問題**で、CLAUDE.md の
診断は正しい。逆に言えば、**Lite-S の順位付けを直せば全体MAEの大半が落ちる。**

実際あなたのTA1 8月計画は Lite-S を毎日20〜40k で通し続けている(8月に黒字で入って
いるのはほぼ Lite-S だけ)。自動立案は Lite-S を後半に寄せている。

### B-4. 照合できているのは FeliCa 全体の一部

- FeliCa の製番行 310 のうち、7〜8月に台数があるのは **55行**(255行は全ゼロ)
- 台帳の101製番と FeliCa の製番が一致するのは **75件**
- carryover除外(同日Line-In+Completion)で 19件中16件が消え、残り **39行**
- 結果、照合できた製番 = **31〜33件**(FeliCa全体の約1割)

**なお、carryover除外は実データ上は妥当だった。** 消えているのは例えば

```
製番 6WMA5ENN (RC-S103/JW16)  Line-In 7/16: 57,600  /  Completion 7/16: 57,600
```

のように**投入と完成が同日・同数**の行で、これは確かに先週までの計画台数の転記であって
実生産ではない。前回レポートでこの除外を「削りすぎ」と書いたが、実データで確認した結果
**この判定は正しい**。訂正する。

母数が31件に絞られること自体は避けられないが、**画面には「FeliCa 310製番中31製番で照合」
と母数を出すべき**(現状は照合できた数だけが出る)。

### B-5. 細かい点

- **計画期間外の日付が端の稼働日に丸められる。** `_nearest_index` は期間外も丸めるため、
  期間外のロットが「照合できた」ことになり誤差が期間幅で頭打ちになる。期間外は `None` を
  返して母数から外すべき。7/01–9/30 の窓で MAE が18.18まで伸びたのは実際のずれだが、
  逆に狭い窓では頭打ちで小さく見える。
- **`_with_offsets` が `lead_offset_by_product` を落とす。** 較正が評価する「現行値」が
  機種別オフセット設定時に別物の計画になる。現 config は未使用なので今は影響しないが、
  Phase 4 を使った瞬間に壊れる。1行で直る。
- **役割ラベルの表記ゆれで照合が黙って0件になる。** 製番(col4)は `.strip()` しているが
  `role == "Line-In"` は完全一致比較。末尾空白ひとつで読み取り0件になる(再現確認済み)。
- **`matched` は完成日のペア数のみ。** 投入日MAEの母数は画面に出ない。
- **TA1 に出てくる機種コード `A22F` / `S113` が `productAliases` に無い。** 今回は台数が
  0なので影響しないが、稼働したら計画から落ちる。
- **サマリーの「TA1 HAL実績反映(日数)」が 0 と出る。** 実績(7/1〜7/17)が計画開始日
  7/29 より前なので窓外になるだけで、動作は正しい。ただ 0 と出ると読み取り失敗に見える。

なお、**自分の計画をそのまま FeliCa 形式にして読ませる往復テストでは全MAEが0**になった。
照合の骨格そのものは健全で、上記はいずれも運用条件と端の処理の問題。

## C. 何を直せば「手計画と同じ」に近づくか

優先順位順。上2つで大半が動く。

| # | 項目 | 実データでの効果 | 難易度 |
|---|---|---|---|
| 1 | A勤限定切替の判定を号機グループ単位(または勤務帯)に変える (A-1) | 納期遅れ 16→10製番、遊休能力 −116,240台、並行機種数が実績の姿に近づく | 中 |
| 2 | Lite-S のような低キャパ機種の順位付けを見直す (B-3) | 完成日bias +15.0 稼働日の解消 = 全体MAEの大半 | 中 |
| 3 | 祝日を config 既定値にする / 照合前のカレンダー取込を必須化 (A-2) | 8/11・8/14 のフル生産割り付けが消える | 小 |
| 4 | 必要日次レートを納期ベースで算出する (A-3) | end_date で 22H/16H が変わる不安定さの解消 | 中 |
| 5 | 上流/下流の期間外セルをWIPとして明示 or 期間を広げて立案 (A-4) | TAL 5〜9%、MIL 5〜13% の欠損解消 | 中 |
| 6 | 照合期間を FeliCa の実範囲に固定して精度を報告する (B-1) | 数字が引用できるようになる | 小 |
| 7 | `_nearest_index` の期間外を `None` に (B-5) / `_with_offsets` の欠落修正 | 較正が実力を測るようになる | 小 |
| 8 | A勤繰下げ警告の集約と文言修正 (A-5) | 本当に見るべき警告が読めるようになる | 小 |

1 と 2 を直したうえで、期間を 7/1–8/31 に固定して `/api/bottleneck/validate` を回し直すのが
次に取るべき数字。現状のベースラインは **完成日MAE 9.42 / bias +5.16 / 照合31製番**。
